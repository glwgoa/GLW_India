GLW INDIA OPS DASHBOARD — FULL IMPLEMENTATION PLAN
====================================================

CONTEXT
-------
Building a Next.js + Supabase ops dashboard covering bookings/vendor SLA
tracking, regional inventory, projects/attendance, and MIS analytics, based
on the supplied architecture spec (dashboard_implementation_plan.txt). Repo:
/home/hrithik/Documents/GLW_India (git remote: github.com/glwgoa/GLW_India).
Connected Supabase project: dpfhlpbccnlvddaokeai ("glwgoa's Project").
Building the full system in one pass, schema applied live via the Supabase
MCP, using Email/Password auth only.

KEY DECISIONS
-------------
1. Scaffold into the repo root, not a nested "dashboard-app/" folder — the
   repo root already is the intended app root.
   Command used: create-next-app --typescript --tailwind --app --src-dir
   (npm rejected the literal directory name "GLW_India" due to uppercase
   letters, so it was scaffolded into a temp dir and merged into the repo
   root; package.json name set to "glw-india-dashboard".)

2. Add profiles.vendor_id UUID REFERENCES vendors(id) — one column beyond
   the literal spec DDL. Without it, "vendor sees only their own bookings"
   RLS has no way to link an authenticated user to a vendor row. All other
   tables are created verbatim as specified in the original doc.

3. "Total Revenue" MIS metric = SUM(projects.budget) per region (no
   orders/invoice-amount table exists in the schema); "Total Orders" =
   COUNT(bookings) per region.

4. Auth users are seeded through the app, not SQL — Supabase Auth requires
   the Auth API for password hashing. Seed migration covers only regions /
   vendors / sla_guidelines / catalog_items / regional_inventory / bookings
   / projects. Test users are created via /register then promoted to roles
   with an execute_sql UPDATE (documented in Verification).

5. GitHub branch protection / CI workflows are OUT OF SCOPE for this pass —
   only the main/development/feature/* convention is documented in the
   README, no GitHub Actions or protection rules are configured.

PHASE 2 — DATABASE MIGRATIONS
------------------------------
Write files under supabase/migrations/ and apply each via the Supabase MCP
apply_migration tool against project dpfhlpbccnlvddaokeai, confirming with
list_migrations after each.

1. 20260801000001_enums_and_extensions.sql
   - pgcrypto extension
   - enums: user_role, sla_status, booking_status (verbatim from spec)

2. 20260801000002_core_tables.sql
   - all 9 spec tables verbatim: profiles, vendors, sla_guidelines,
     regions, catalog_items, regional_inventory, bookings, projects,
     attendance
   - plus profiles.vendor_id (decision #2)
   - indexes: profiles(vendor_id, region_id), bookings(assigned_vendor_id,
     region_id, sla_status), projects(assigned_vendor_id, region_id),
     regional_inventory(region_id), attendance(user_id)
   - ALTER PUBLICATION supabase_realtime ADD TABLE bookings,
     regional_inventory;

3. 20260801000003_functions_and_triggers.sql
   - handle_new_user() trigger: auto-creates a profiles row (role
     'employee') on auth.users insert
   - SECURITY DEFINER helpers: get_user_role(), get_user_region(),
     get_user_vendor() (avoids RLS self-recursion on profiles)

4. 20260801000004_rls_policies.sql
   - enable RLS on all 9 tables; policies:
     * profiles: self row + admin unrestricted
     * vendors: admin unrestricted; vendor sees/updates own row via
       vendor_id = get_user_vendor(); PM read-only
     * sla_guidelines: admin write; vendor/PM read scoped
     * regions / catalog_items: readable by all authenticated;
       admin-only writes
     * regional_inventory: readable by all authenticated; admin
       unrestricted writes; PM writes scoped to region_id =
       get_user_region()
     * bookings: admin unrestricted; vendor scoped to assigned_vendor_id
       = get_user_vendor(); PM scoped to region_id = get_user_region();
       insert restricted to admin/PM
     * projects: same region/vendor scoping pattern as bookings
     * attendance: user sees/creates only own rows (user_id = auth.uid());
       admin/hr unrestricted

5. 20260801000005_mis_views.sql
   - 4 security_invoker = true views: vw_vendor_response_efficiency,
     vw_region_revenue_orders, vw_monthly_attendance_summary,
     vw_sla_compliance_by_region (each role automatically sees only the
     rows their table RLS already permits)

6. 20260801000006_seed_data.sql (idempotent, on conflict do nothing)
   - 4 regions, 5 vendors + their SLA guidelines, 8-10 catalog items,
     cross-joined regional_inventory (some rows near low-stock threshold),
     6-8 bookings (mixed status/sla_status, some near-deadline, some
     already breached), 4-5 projects

7. Run get_advisors (security) after this phase to catch missed RLS gaps

PHASE 6 — MODULE 1: BOOKINGS & VENDOR ATTRIBUTION
----------------------------------------------------
REVISED (user decision, superseding the original realtime/auto-flip design):
bookings are NOT realtime and sla_status is NOT auto-updated. Staff set
status and sla_status manually via dropdowns; RLS still governs who can
write which rows.
- src/lib/sla.ts — computeSlaHint(deadline, status) pure function +
  countdown formatter. Purely informational, never written to the DB.
- src/hooks/use-polling-bookings.ts — initial fetch + setInterval re-fetch
  every 30s (no websocket/postgres_changes subscription)
- src/components/bookings/sla-badge.tsx — shows the persisted sla_status
  badge plus a live countdown + due-soon/overdue hint label recomputed
  every 30s client-side for display only
- src/components/bookings/bookings-table.tsx — manual status and
  sla_status Select dropdowns per row; admin/PM also get a vendor
  assignment Select
- src/components/bookings/bookings-client.tsx — wraps the table with the
  polling hook and a manual "Refresh" button
- src/app/(dashboard)/bookings/page.tsx — server-fetches initial bookings
  (joined to region/vendor names) + vendor list for admin/PM
